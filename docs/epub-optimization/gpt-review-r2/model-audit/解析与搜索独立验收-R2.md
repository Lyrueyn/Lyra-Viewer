### D02 · F05 · P1/P2 · 查询/索引身份仍共用，取消后不能可靠重启

位置：[search.js:37](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r2/candidate/search.js#L37>)、[ensureIndex:39](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r2/candidate/search.js#L39>)、[search:80](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r2/candidate/search.js#L80>)。

- **M05 热缓存取消失效：** 先 ensureIndex；调用 search；立即 cancel；等待 search，仍正常返回 1 条。原因是 query 在 await ensureIndex 之后才读取 `_generation`，把取消后的新代次当成本次合法代次。
- **M06 冷索引取消牵连新查询：** 挂起 getSectionPlainText；启动 old 查询；cancel；立即启动 new 查询；放开挂起读取。两者都 `rejected: 搜索已取消`。新的 ensureIndex 复用了尚未收尾、注定失败的 `_building`。
- **M07 单章扫描无取消点：** 热索引内一个合法大小的章，`x ` ×4,194,304；查询前排入 0ms cancel 定时器。扫描返回 4,194,304 total、1000 个展示结果时，取消定时器仍未执行。本机一次约 110ms，仅是该 Node 输入的耗时，不外推为所有客户端冻结时长。源码 while 扫描无 await，索引读取单大章时也没有章内分块。

R3 应分别管理书籍、索引构建和查询身份；调用取消后立即开始的新查询不能挂在旧失败 Promise 上；索引与扫描在长单章内都要能让出执行权。

### D04 · F05 / 统一模型 · P2 · “同一模型”仍不是“可见正文模型”

位置：[buildTextModel:129](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r2/candidate/epub-book.js#L129>)无条件遍历元素子节点；[正文清洗:554](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r2/candidate/epub-book.js#L554>)保留 hidden 等结构；[纯文本:640](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r2/candidate/epub-book.js#L640>)只删除固定 blocked 标签后直接建模。

M12 最小内容包含：

```html
<p>A<span hidden>HIDDEN_SECRET</span>B</p>
<aside hidden epub:type="footnote">FOOTNOTE_SECRET</aside>
<details><summary>Summary</summary>CLOSED_SECRET</details>
<svg xmlns="http://www.w3.org/2000/svg">
  <defs><text id="unused">SVG_DEF_SECRET</text></defs>
  <desc>SVG_DESC_SECRET</desc><text>SVG_VISIBLE</text>
</svg>
```

以上五种默认不可见字符串均各返回 1 个搜索命中，真实 DOM Range 指向对应隐藏文本；可见的相邻文字 AB 却返回 0。prepared HTML 中 hidden 仍保留，所以这不是清洗后主动把隐藏内容展开再搜索的策略。

节点与索引使用同样串联规则，确实解决了一部分坐标不一致；但没有解决“哪些节点是正文”的语义。隐藏脚注、关闭 details 内容与 SVG defs/desc 不能仅因为有 textContent 就视为当前可见正文。此项证明 DOM 语义和模型行为，不声称已测浏览器点击隐藏命中后的页号。

R3 需要明确并共享可见正文规则；若选择允许搜索未展开脚注/details，则必须给出可达的显示/展开流程，而不是仅返回零几何范围。不要简单把所有脚注都排除：当前可见的脚注文字、目标链接与返回位置仍应保留。出版社样式被移除后的语义也应固定，再建立稳定 UTF-16 映射。

### D06 · F14 · P2 · 字体混淆识别未校验算法和资源类型

合成输入中正文保持明文，以隔离“声明分类”行为；上述错误不代表真正受保护正文已经解密，也不是 DRM 绕过证明。R3 应按 EncryptedData 逐项验证精确算法、CipherReference 一次解析结果和 manifest 字体类型；只有全部受保护目标都是受支持的字体混淆才继续使用系统字体。未知算法/非字体/无法解析目标应给出准确的“不支持”说明。

### D07 · F13 / F03 · P1/P2 · 同书旧章节资源迟到后留在缓存

位置：[epub-book.js:513](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r2/candidate/epub-book.js#L513>)只检查整本 `_destroyed`；[prepareSection:538](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r2/candidate/epub-book.js#L538>)没有章节任务身份；[releaseResourcesExcept:676](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r2/candidate/epub-book.js#L676>)只处理已登记 URL；[reader.js:760](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r2/candidate/reader.js#L760>)–761 发现旧任务时直接 return；[782 行](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r2/candidate/reader.js#L782>)只在当前章提交时清理一次。

M10 时序使用原 prepareSection 和真实 ZIP，只有旧图 readBytes 人为延迟：

1. 旧章 A 读 slow-a.png，旧章 B 读 slow-b.png，均挂起。
2. 最新章 C 准备 current.png 成功，执行真实 releaseResourcesExcept(C.resources)。此时 Map 只有 current.png。
3. 放开 A/B，两个旧 prepareSection 都结束；书本没有销毁，所以两个旧 URL 正常创建并登记。
4. 静止后 pending=0，但 Map 仍有 current.png、slow-a.png、slow-b.png 三项，其中两项已经不属于当前章。

这证明 M01/M02 的修复不能覆盖任务书“资源属于具体书/章节任务”的全部要求。当前实现不会因为本例而释放 C 正在使用的图；本例证明的是旧任务资源漏收。更多并行旧章可留下更多资源，直到下一次清理或整本销毁。没有本次浏览器图片损坏/内存趋势结论。

R3 应对 prepared/加载任务建立资源引用或租用关系，任务失效时释放自己的引用；共享路径仍由当前有效使用者保护。只增加一次全局 clear 会重新引入撤销新章 URL 的问题。
