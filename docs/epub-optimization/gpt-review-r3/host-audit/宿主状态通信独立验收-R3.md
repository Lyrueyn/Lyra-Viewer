## 3. 剩余问题与最小复现

J01 由原字号 input 18→原300ms防抖→字号32→原300ms防抖驱动，宿主实际授予 `639287159852507025` 与 `639287159852507026`，原 JS 两次回传都成 `639287159852507000`。两次请求均 PREFERENCE_STALE；实际偏好文件不存在，pending仍有fontSize，UI“设置未保存，可重试”。原始 long 与 JS 往返字面值都在[结果:10](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r3/host-audit/runs/r3-release-report/client-results.json#L10>)及 wire 中。

这是默认代码路径的跨语言数值错误，不依赖人为输大数、系统时钟倒退或延迟。具体哪些 ticks 恰好可往返取决于数值，本报告不把两次结果外推成失败百分比。建议采用不丢精度的宿主不透明字符串授权标识，或明确受限的安全整数空间，并在协议中声明；不能仅在 C# long 内自测排序。

### HA3-03 · P1 · finalize 的 ok 不代表保存成功，也未等完后续 pending

位置：[reader:232](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r3/candidate/reader.js#L232>)在已有flush时只返回该promise，[reader:277](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r3/candidate/reader.js#L277>)把新pending安排在80ms后；[reader:1302](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r3/candidate/reader.js#L1302>)与下一行吞掉两个flush的false，只在throw时令ok=false。两个flush内部本就catch并return false。

- **J05 保存失败仍成功回执：** 偏好和位置提交返回受控WRITE_FAILED，原handler仍发精确requestId/session、`ok:true,revision:0`；pending字号和failedSaves均保留，原C#宿主立即关闭。故障是明确注入的失败分支，不宣称日常磁盘自然报错。
- **J06 在途18后新32被遗漏：** 字号18已由原C#落盘但回执暂留；真实input改32；送入原Closing产生的host.finalize；释放18回执。关闭只等到了旧flush，磁盘仍18、pending仍32、80ms重试还没执行，已发`ok:true,revision:1`并触发原宿主关闭。该用例的等待/投递受控，不是自然延迟率测量。

证据：[J05](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r3/host-audit/runs/r3-release-report/client-results.json#L241>)、[J06](<F:/DSH/LocalMediaPlayer-Workspace/docs/epub-optimization/gpt-review-r3/host-audit/runs/r3-release-report/client-results.json#L273>)。应冻结最终目标并等待所有在途和后续必要提交结清，再构造成功回执；失败返回false且说明哪部分未确认。无修改的false需与失败的false分开建模。

J08/H07 确认宿主1.5s期限有效，client请求期限仍3s；timeout可退出是正确的有界性，不能因此把超时算成功。当前丢失并非因为没有handler，R3已经有handler，而是完成条件不准确。
