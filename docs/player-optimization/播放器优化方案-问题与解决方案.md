## 0. 一页速览（TL;DR）

### 0.1 一句话结论

播放器的**内核设计在水准之上**（音频主时钟三铁律、设备丢失双阀、WASAPI 独占协商、BT.2390 色调映射、GPU 弹幕、AI 字幕都是硬功夫），但**"最后一公里"的工程债很重**：当前引擎源码与界面之间的导出契约已经断裂（判死提示整条失效）、4K 播放的帧队列背压判据写错（解码线程空转丢帧）、音频链有 3 颗潜伏雷、弹幕/前端若干 UI 线程重活会冻结界面，还有一条"假播放结束→无限重播"的现场缺陷（同一文件循环 37 次）；画质侧则卡在"有基础滤镜、无真正缩放核/色彩管理/硬解"的阶段。**建议先花约 6 人日修最关键的 10 条 P0（全部 16 条约 8~10 人日），再按"画质 → 性能 → 体验 → 架构"顺序推进**。

### 0.2 最严重的 16 个问题（P0，编号与 §3 一致；★=有现场日志证实）

| # | 问题 | 影响 | 工作量 |
|---|---|---|---|
| P0-1 / Q0-1 ★ | 当前引擎源码**丢了 `DshEngine_GpuDead` 导出**，界面每秒调用、异常被吞（现场日志 24 次 `EntryPointNotFoundException`）→ 显卡判死提示链整条失效；且导出面无版本号，仓库两个 DLL 各缺不同符号 | 白屏（DEVICE_REMOVED）时用户完全不知道发生了什么；DLL/界面失配时界面会"说假话" | 0.5 天 |
| P0-2 / R0-14 | **HDR 内容全程在 PQ 码值域做插值/滤波**（先滤波后解码）：1000+10 nit 相邻纹素平均后解码只剩 119 nit（线性正解 505 nit，**-76%**），1000/1 nit 是 **-89%** | 所有非 1:1 显示（如 140% 缩放、窗口化）整幅 HDR 高光被系统性吃掉；这是当前画质最大硬伤，但**修起来只要改两个 shader 的 8 行** | 0.5~1.5 天 |
| P0-3 / R0-15 | 「4×4 展宽 Catmull-Rom」**不是低通**：2:1 时 |H(0.5)|=**1.000**、|H(0.25)|=0（正确 2×2 box 应为 0/0.707）；16 fetch 比 4 fetch 的 box 还贵 | 4K→1080p 摩尔纹/混叠必然严重；"缩小后画面发脏"的直接原因 | 0.5~1 天 |
| P0-4 / E0-2 | 帧队列"满"判据用 `QMAX(16)`，实际容量是 `qCap()`（4K 只有 5）→ 解码线程一次跑满 300 帧、约 295 帧解完即丢 | **4K/2K 播放 CPU 打满、画面一顿一顿、seek 从毫秒退化到秒级**（最可能是"4K 卡"的根因，需一次实测确认） | 0.5 天 |
| P0-5 / E0-3 | 解封装请求是**单槽**：换片(load) 与拖进度条(seek) 并发时 load 被覆盖 | 换片偶发"新视频永不加载/黑屏"，要再点一次 | 0.5 天 |
| P0-6 / U0-4 | 白屏页「重新启动播放器」拉起新实例**没带 `--video`**（新进程撞单实例锁自杀）；多窗模式还会把主窗口进程误判成新实例并关掉视频窗 | 白屏时唯一的自救按钮 = 关掉播放器 | 0.5 天 |
| **P0-7 / U0-15 ★** | **假"播放结束"→ 单集循环无限重播**（实测同一文件循环 **37 次**，间隔恒 3m57s）：音轨 237s 提前 EOF → 音频主时钟冻结 → 位置停在 235.633s → 只凭 `stalled=True`（`nearEnd=False` 也判）就触发重播 | 音轨比视频短的片子会在片尾前无限自循环；用户看到"播到 3m56s 就跳回开头" | 1 天 |
| P0-8 / A0-5+A0-6 | 独占 24bit 路径**写入越界**（按 24-bit packed 建格式却按 int32 写 4 字节）＋ int16 输出**无钳位无抖动** | 前者是潜伏的堆越界/强噪声；后者一旦有 >0dBFS 过冲（AAC 过冲、200% 音量）就是满幅爆音 | 1 天 |
| P0-9 / A0-7 | seek 后**不冲刷音频设备缓冲**（`devFlush` 消费分支是空实现） | 每次 seek 残留最多一个设备缓冲（独占 20ms）的旧音频，且端点账本错位 → seek 音画对不齐 | 0.5 天 |
| P0-10 / D0-8 | 改弹幕屏蔽词/刷新弹幕会调用 `DshEngine_SeekJump` → **真做一次视频 seek** | 每敲一个字符 = 画面闪一下、音频断一下、进度条抖 | 0.3 天 |
| P0-11 / D0-9 | 喂全量弹幕时在 **UI 线程逐字 FreeType 测宽** | 1 万条×12 字 = 12 万次 FT 调用；10 万条级 → 单帧数百 ms~数秒 UI 冻结 | 1 天 |
| P0-12 / D0-10 | 弹幕出生**无单帧上限**、无停摆恢复快进 | 渲染回调停摆（遮挡/最小化）恢复后一帧灌几百条 → 几百 ms 冻结 + 屏幕瞬间糊满 | 0.5 天 |
| P0-13 / D0-11 | 窗口尺寸一变就**重建 4096² 图集（32MB）+ 重编两个 HLSL + 重开 FreeType**，无去抖 | 拖动窗口边缘明显卡顿；是"图集反复创建"告警来源 | 0.5 天 |
| P0-14 / B0-12 | 后端 HTTP 层**无超时/无请求体上限/无线程上限/500 回吐异常原文** | 半开连接可永久占线程（后端"假活"）；畸形大 body 打爆内存 | 0.5 天 |
| P0-15 / B0-13 | 本地服务 **CORS `*` + 无鉴权 + path 全放行** | 任意网页可用无需预检的 GET 枚举媒体库、探测本机任意文件 | 0.5 天 |

### 0.4 目标（验收口径，详见 §6）

- 稳定性：连续播放 2 小时 0 崩溃；`DSH_TEST_DEVICE_LOST=1` 注入后判死提示 1s 内出现、换片可自愈；拔插耳机/切默认设备 2s 内自动恢复。
- 性能：4K60 HDR→SDR 播放 CPU < 40%（现软解接近打满）、GPU < 60%、呈现帧耗时 p99 < 16.7ms、内存 < 1.2GB；1080p60 内存 < 700MB。
- 播放响应：本地 SSD 打开媒体 < 500ms；seek→首帧显示 < 300ms（现在 4K 精确 seek 可达 1s+）。
- 音画：A/V 偏差稳态 |x| < 20ms（含 atempo/设备延迟补偿）；音频欠载 0 次/60s（0.5~4 倍速全档）。
- 画质：4K→1080p 缩放 vs ffmpeg lanczos 参考 RMS 再降 20%+；带通 zoneplate 混叠能量 −6dB；渐变平台长度 < 6px（现有 5px 需保持）；HDR→SDR 与参考 PSNR 保持 ≥ 90dB；HDR 直通逐字节不变。
- 日志：正常播放 10 分钟日志增量 < 200KB，单文件超 8MB 自动轮转。

## 2. 播放器现状全景

### 2.1 架构与数据流

```
┌────────────────────────────── WinUI 3 前端（WinUIGui.exe，.NET 10）──────────────────────────────┐
│  MainWindow（视频库/下载/合集/扩展中心）   VideoWindow（播放窗口，6018 行）                         │
│     · 单实例 Mutex；--video <path> 走独立进程（多视频窗口模式）                                    │
│     · VideoWindow 内：CompositionTarget.Rendering 每显示帧 → UpdateDanmaku() → DshEngine_Present() │
│     · 7 个定时器：50ms 进度 / 120ms 字幕 / 800ms AI 字幕 / 1s 判死看门狗 / 2s 渲染看门狗 / 2.5s 控制条… │
└───────────────┬───────────────────────────────────────────────────────────────────────────────────┘
                │ P/Invoke（38 个 DshEngine_* 声明；引擎实际 41 个导出，二者已不同步）
┌───────────────▼───────────────── dsh_engine.dll（C++ / MinGW，全局单例）───────────────────────────┐
│ 解码线程 DecodeLoop                                                                                 │

│ 音频线程（audio_out.h，自带独立 demuxer）                                                            │

│ UI 线程 Present()                                                                                   │
│   弹出到期帧 → Vulkan 渲染到 D3D11 共享纹理（画质滤镜/HDR）→ D3D11 CopyResource → 叠 GPU 弹幕 → Present│

┌───────────────▼────────────── Python 后端（stdlib_server.py → services.py + SQLite）──────────────┐
│ B站/YouTube 解析与下载、B站弹幕/评论/CC字幕、Whisper AI 字幕、AI 增强链（Real-ESRGAN/RIFE/降噪/重采样）│

└───────────────────────────────────────────────────────────────────────────────────────────────────┘
```

**关键事实**（会影响优化方向）：

1. **播放器不依赖后端**：`DshEngine_OpenMedia` 直接读本地文件；后端零流式接口（全仓无 HTTP Range/206），在线视频只能"整段下载后播放"。
2. **引擎是全局单例**：同一进程只能有一个视频引擎；多视频窗口 = 每个视频独立进程。
3. **渲染默认 Vulkan**（`dsh_engine.cpp:1484` 显式 `g_useVulkan=true`，`DSH_GRAPHICS=d3d11` 才回退 D3D11）；但 **D3D11 仍是最终呈现者**（WinUI `SwapChainPanel` 只认 DXGI 交换链），Vulkan 渲染完要整帧拷贝回 D3D11 再叠弹幕。
4. **解码是纯软解**（无硬解路径）：4K HEVC 靠 16 线程软解 ~140fps；所有帧经 sws 转 BGRA 后走 CPU 内存。
5. **音频独占默认关**（`video_player_settings.exclusive=false`），共享模式下设备格式 = 系统混音格式。

### 2.2 能力矩阵（已实现 / 半实现 / 未实现）

| 能力 | 状态 | 说明与缺口 |
|---|---|---|
| 本地视频播放（H.264/HEVC/AV1…） | ✅ | FFmpeg 软解；48kHz 音频；多音轨只取第一条 |
| 10bit / HDR10（PQ） | ✅ | HDR→SDR BT.2390、HDR 直通（10bit PQ 交换链 + MaxCLL 元数据）已逐字节验证 |
| HLG HDR | ❌ | `hdr_convert.h:23` 明确"暂不按 HDR 处理" → 当 SDR 播（发灰/色偏） |
| Dolby Vision | 🔶 | 仅当 HDR10 基础层播；profile 5（IPTPQc2）会偏色，无 RPU 解析 |
| 硬解 / 零拷贝 | ❌ | 无 D3D11VA/Vulkan Video 路径；4K 全靠 CPU |
| GPU 画质滤镜 | 🔶 | Vulkan 路径有：4×4 展宽 Catmull-Rom 缩小 + 3×3 平滑式 deband + 静态 Bayer 抖动（默认 all，无 UI 开关只能靠 `DSH_QUALITY`）；**但缩放核不是低通、HDR 在 PQ 码值域滤波（两处硬伤，见 R0-14/R0-15）**；放大无滤镜；D3D11 路径完全没有滤镜；ICC/3D LUT、锐化、去隔行、FSRCNNX 在当前线**全部不存在**（只存在于已归档老线） |

### 2.3 已有的亮点（优化时不要破坏）

1. **A/V 主时钟**：以音频 `mediaUs()` 为单调锚 + 墙钟插值 × 倍速，三条铁律（锚单调/锚间插值/绝不做逐次比例校正）写在 `dsh_engine.cpp:259-302`，是弹幕不抖、倍速不漂的基础。
2. **设备丢失双阀**：60 秒窗口最多 3 次重建（成功也计数）+ 抖动检测 + 判死停机，把历史上"41 次重建风暴→蓝屏"压住了（`dsh_engine.cpp:2352-2422`）。
3. **WASAPI 独占协商**：32f→32i→24i→16i 逐级探测 + `IsFormatSupported` 预检 + 失败不再静默回退（`audio_out.h:805-877`）。
4. **swr 带限重采样**：filter_size=64/phase_shift=10，44.1k→48k 与 ffmpeg aresample 逐位一致（THD+N −98.55dB）。
5. **BT.2390 色调映射 + "内容峰值当白场" + 色相保持**（`shaders/video_blit.frag`），HDR 直通逐字节一致、HDR→SDR PSNR 95.8dB 的历史验收结论仍成立。
6. **GPU 弹幕字形图集**：GPU 侧 0.04ms/帧（从 CPU 24.54ms 降下来），HDR 直通下的弹幕 PQ 换算也做对了。
7. **诊断体系**：32+ 个 `DSH_*` 开关、崩溃处理器写日志、`diag.ps1` 诊断包——这次能审得这么细，靠的就是这些基础设施。

## 4. 分模块详解与解决方案

> 本章只对 **P0/P1** 给完整落地改法（改哪个函数 / 哪几行 / 怎么验收）；P2 的批量小项见 §3.3。工作量按 1 人（熟悉本项目）估算。

### 4.1 引擎核心与播放管线（E / Q0 系列）

#### 4.1.1 先修"最短路径"三件事（合计约 1.5 天，收益最大）

**① 补 `DshEngine_GpuDead` 导出 + 加版本协商（Q0-1，0.5 天）**

- 在 `dsh_engine.cpp` 的 `DshEngine_Present`（`:2544`）前补三个导出：
  ```cpp
  extern "C" __declspec(dllexport) int WINAPI DshEngine_GpuDead(){ return g_gpuDead ? 1 : 0; }
  extern "C" __declspec(dllexport) int WINAPI DshEngine_GetApiVersion(){ return 2; }     // 以后加接口就 +1
  extern "C" __declspec(dllexport) void WINAPI DshEngine_GetBuildInfo(char* buf,int n){
      snprintf(buf, (size_t)n, "%s %s | %s", __DATE__, __TIME__, "v2"); }
  ```
- C# 侧加 `DshNative.Probe()`：用 .NET 10 的 `NativeLibrary.TryGetExport` 逐个探测（不要靠 try/catch P/Invoke），生成 `EngineCapabilities` 位集；`Init` 后校验 `GetApiVersion()`，不匹配或关键导出缺失时在界面明示"引擎与界面版本不匹配（缺少 X）"，禁止调用缺失接口。
- **验收**：`objdump -p dsh_engine_vsr.dll` 含全部符号（42+）；`DSH_TEST_DEVICE_LOST=1` 注入 → 3 次退避判死后 **1 秒内**白屏横幅出现、控件置灰、自动暂停；换片（引擎会在 `:1515-1524` 尝试自愈）后横幅消失；把 10-18 旧 dll 放回 bin → 设置页显示"引擎版本过旧"，而不是"本机未检测到 RTX 显卡"。
- **事实更正**（避免按子审计 05 的错误结论去修）：经主审计用 objdump 复核，`dsh_engine_vsr.dll`（10-23）**有全部 6 个 RTX 导出**；缺少的只有 `GpuDead`。旧 `dsh_engine.dll`（10-18）才是"有 GpuDead、没有 RTX 导出"的那份。所以真正要做的是：**修源码补 GpuDead + 版本协商 + 让部署永远用新构建**，而不是去补 RTX 导出。

**② 帧队列背压判据（E0-2，0.5 天）**

**③ 请求优先级（E0-3，0.5 天）**

- 最小改动：`SeekPreview/SeekJump` 的 `g_reqType.store(2/3)` 改为 CAS——`int expected=0; if(!g_reqType.compare_exchange_strong(expected, 3)) return;`（load 已经占槽时丢弃本次 seek，UI 侧下一次拖动会再发）。

#### 4.1.3 每帧数据通路：帧池 + 去拷贝（E1-3，2 天）

现状 4K 每帧：`sws_scale` 写 rgba（1 次）→ 逐行 `memcpy` 到新 vector（1 次）→ Vulkan `uploadFrame` 再 `memcpy` 进 staging（1 次）→ GPU；每帧还有一次 33MB 分配/释放。

改法：
1. 建 `cap` 个 slab（一次分配 `cap × w × h × 4`，或每个 slab 一个 vector 但全部预分配），队列元素存 `{slabIndex, pts, w, h}`，不再 move vector。
2. `sws_scale` 直接以 slab 为目标：`dst[0]=slab.data(); dstStride[0]=w*4;` → 删掉 `:2273-2274` 的逐行 memcpy。
3. Vulkan 路径：`sws_scale` 直接写**持久映射的 staging 内存**（`stagePtr`），跳过一次 CPU 拷贝——前提是"只解码一帧、立刻上传"的时序；若仍要帧队列做节奏，则把"CPU 队列"和"GPU 纹理环"分开：解码线程产出 slab → 上传到 GPU 纹理环（N 个纹理）→ Present 只选纹理。
4. pop 后 slab 归还池，不 `clear()`。

**验收**：`[性能]` 行对比：1080p D3D11 上传从 ~0.27ms 降到 <0.15ms、Vulkan 从 0.75ms 降 15~25%；4K 分配器压力消失（进程私有内存不再周期性锯齿）；画面逐帧 A/B 与改前一致（PSNR=inf）。

#### 4.1.4 打开/预览体验（E1-6/E1-8）

- **E1-6 预览只出一帧**（1 天）：`DoSeek2(preview=true)` 置 `g.previewOneFrame=true`；`DecodeAhead` 在 preview 下取到"pts ≥ 落点"的第一帧入队后立即 `break` 并清标志；或临时设 `g.cc->skip_frame=AVDISCARD_NONREF` 到出帧为止。**验收**：4K 长 GOP 文件拖拽，单次预览耗时 ≈ 一帧解码时间；进度条跟手。
- **E1-8 `g_speedReq` 原子化 + 随 load 快照**（0.5 天）：改 `std::atomic<float>`；`OpenMedia` 时把当前倍速写入 `g_reqSpeed`，`LoadMedia` 读快照（保持"先设速率再开音频"的约定）。

#### 4.1.5 改造后的目标形态

```
[解码线程] tmp 资源 open/probe → 锁内交换指针 → 解帧 → sws→slab（sws 直写）→ 把 slab 上传到 GPU 纹理环 → 记录 {texIdx,pts}
[音频线程] 独立解码线程 → 环 → 渲染线程只做 GetBuffer/ReleaseBuffer（见 4.3）
[UI 线程] Present：只等"上一帧"fence（in-flight=2~3）→ 渲染 → 交叉 API 同步 → 弹幕 → Present
[状态] DshEngine_GetState/GetStats 结构化导出；日志分级+轮转
```

### 4.2 渲染与画质（R 系列）

#### 4.2.1 两个必须立刻修的画质硬伤（合计约 1~2.5 天，收益最大）

**① HDR 线性光滤波（R0-14，0.5~1.5 天）**

- 根因：`video_blit_quality.frag` 在 PQ 码值域做缩放（`:122`）和 deband（`:123`），直到 `:133` 才 `pqToLin`。PQ 是感知编码，码值域线性插值 ≠ 线性光插值；高光相邻像素（如 1000nit 与 10nit）平均后在码值域解码只有 119nit。
- 改法（只碰 SDR/色调映射模式，**不碰 10bit 直通**）：
  ```glsl
  vec3 sampleLinear(vec2 uv){ vec3 c = texture(tex,uv).rgb; return pc.mode>0.5 ? vec3(pqToLin(c.r),pqToLin(c.g),pqToLin(c.b)) : c; }
  vec3 encodeBack(vec3 c){ return pc.mode>0.5 ? vec3(pqFromLin(c.r),pqFromLin(c.g),pqFromLin(c.b)) : c; }
  ```
  `filterScale` / `filterDeband` 内部改用 `sampleLinear`，返回前 `encodeBack`；`mode>1.5` 的直通分支保持 `:114` 的早返回不动。
- 成本：每像素多 2 次 `pow` 链（PQ 的 pow 较贵），可先在 HDR 模式限定；实测预期 +0.1~0.3ms/帧（1440p）。
- **验收**：取同一 HDR 帧，关/开线性滤波对比：高光边缘最亮像素亮度误差 <5%（当前 −40%~−89%）；HDR→SDR 与参考 PSNR 不降（≥90dB）；10bit 直通路径逐字节不变（`DSH_HDR_PASSTHROUGH` A/B）。

**② 换缩放核（R0-15，0.5~1 天）**

- 止血：`step ≥ 1.8` 时先换 4-tap **2×2 box**（每个源像素权重 1/4；等价 4 fetch 双线性缩小），混叠增益 1.000 → 0。
- 目标：8-tap 可分离带限核（对每个 tap 用 box 积分权重，或 Lanczos-lite 加 window）；水平/垂直两 pass 或单 pass 8 fetch。
- 放大：加一档 CR/Lanczos-lite（质量档位：`off` / `scale`（现有）/ `hq`（新核））。
- **验收**：`zoneplate_1080p.mp4` 4K→1080p 缩放，混叠能量 −6dB（对比现核）；与 ffmpeg lanczos 参考 RMS 再降 20%；帧耗时增加 ≤1ms（4K）——用现有 `measure_banding.py`/新增 zoneplate 频谱脚本量化。

#### 4.2.2 SDR 色彩正确性、HDR 元数据与判定（R1-19/R1-20/R1-15）

- **R1-19 矩阵/范围**（0.5 天）：`dsh_create_sws()` 里把 colorspace 设置从"HDR 才设"改成**始终设置**：`inCoef` 按 `h.space/h.prim` 选 601/709/2020，`srcRange` 按 `h.range`，输出 RGB full。**验收**：BT.601 SD 测试片（工作区 `test709.mp4` 等）饱和度与 ffmpeg 参考 ΔE<1；全范围（JPEG range）内容黑位不再被切（0→16 问题消失）。
- **R1-20 HDR 元数据/判定**（1 天）：`MaxFrameAverageLightLevel` 用真实 MaxFALL（或保守固定值）；内容峰值按窗口统计而不是永不下落的 `max`；"显示器是否 HDR / SDR 白场"改成**按窗口所在显示器**判定（`MonitorFromWindow` + `GetDisplayConfig`），并监听显示器切换/唤醒（WM_DISPLAYCHANGE）。**验收**：双屏（一 SDR 一 HDR）打开 HDR 视频，放在 SDR 屏上不应误开直通；同帧直通亮度与参考差 <3%。
- **R1-15 HLG**（1 天）：`hdr_convert.h` 增加 `curve` 字段（PQ/HLG），HLG 走 BT.2100 HLG EOTF + OOTF（`linear = pow(HLG_inv(x), 1.2)` 近似）后进入现有 BT.2390 链路；sws 输出仍 10bit。**验收**：`ffmpeg -color_trc arib-std-b67` 合成 HLG 测试片不再发灰；与参考 HLG→SDR 帧 PSNR ≥ 35dB。

#### 4.2.3 性能链路（R1-9 / R1-10 / R1-21，合计约 4~5 天）

- **R1-9 Vulkan 同步重构**（2 天）：`uploadFrame` + `render` 合并为**一次** command buffer 提交；3~4 帧 in-flight（每帧独立 cb/fence/staging 环，可用 `MAX_FRAMES_IN_FLIGHT=3`）；Present 只 `WaitForSingleObject(fence[frame])`。跨 API 与 D3D11 的同步改用 `VK_KHR_external_semaphore_win32` + `ID3D11Fence` 共享句柄（替代全同步等待），先把"导出共享 fence"的可行性探针跑通再改主路径。**必须先做 A/B 逐字节验证**（SDR/HDR 直通/色调映射三模式）+ 30 分钟压力（含分辨率切换）不掉设备。保留 `DSH_VK_SYNC=legacy`。
- **R1-10 去整帧 CopyResource**（2~3 天，可后置）：方案 A 最划算——把弹幕合成也交给 Vulkan（弹幕字形图集从 D3D11 纹理共享给 Vulkan，或干脆把 `DanmakuGpu` 改成 Vulkan 版），D3D11 只负责 `Present`；方案 B（后缓冲共享给 Vulkan 直接渲染）需先做"DXGI flip 后缓冲能否被 Vulkan import"探针。
- **R1-21 减少白拷与重绘**（1 天）：缓存两个后缓冲的 RTV（用 `GetCurrentBackBufferIndex` 选），只在 Resize/重建时失效；加 dirty flag：无新视频帧且弹幕顶点无变化时**不重绘**（暂停/静止画面省 GPU 与电）；`Clear` 只在必要时做。预期静止时 GPU 占用 −30~60%。

#### 4.2.4 VSR、色彩管理与能力补齐（R1-13/R1-14/R1-16/R1-17/R1-18）

- **R1-14 VSR 修三件事**（1.5 天）：①VSR 输出纹理建共享句柄 → Vulkan import（复用 vkTargetTex 的 interop 代码），去掉 CPU 回读，预期 7.2→2~3ms/帧；②目标分辨率不要"强制 2× 再双线性缩回"，改成"按窗口大小 + 质量档决定超分倍数"，缩回用 R1-11 的新核；③`Rv_Probe` 用引擎实际选的适配器；修 `s_n` 统计少报。
- **R1-13 色彩管理**（3 天）：quality shader 加 `binding=1 Texture3D lut33`（四面体插值，33³），C++ 侧加载 `.cube`（可移植老线 `lut.cpp`）；lcms2 工具移植老线 `icc_to_lut.cpp/icc_calibrate.cpp`（已在老线验证过）；启动时 `GetICMProfile` 读当前显示器 ICC → 转 LUT（缓存到 `data/`）；输出色彩空间按显示器能力（P3 显示器可输出 `RGB_FULL_G22_NONE_P3`，HDR 直通走 10bit）。设置页给"校色文件/开关/强度"。
- **R1-16 硬解**（3 天，高风险）：先写探针验证"D3D11VA 解出 NV12/P010 纹理 → NT 共享句柄 → Vulkan import → shader NV12/P010→RGB（含 chroma 上采样）"这条零拷贝链；通了再接主引擎（`DSH_HWACCEL=d3d11va|none`，默认软解）。预期 4K CPU 从接近打满降到 20~30%，功耗显著下降。**失败回退开关必须默认 back 到软解**。
- **R1-17 10bit SDR 通路**（1 天）：`dsh_detect_hdr` 对"非 PQ 但 >8bit"也选 `X2BGR10LE`，输出端 dither（复用现有抖动）；sws 参数至少 `SWS_ACCURATE_RND`。
- **R1-18 D3D11 画质对齐**（2 天）：把 scale/deband/dither 写成 HLSL 版（`video_shaders.h` 里已有 HLSL 字符串模式），D3D11 路径默认启用；Vulkan 回退时 UI 提示"画质滤镜不可用"。

#### 4.2.5 渲染/画质验收清单

1. 4 组 A/B 逐字节：SDR 直搬 / HDR→SDR tone-map / HDR 直通 / 灰度/平面内容——改前后 PSNR=inf（除刻意改动的项）。
2. HDR 高光误差：<5%（线性光滤波后）。
3. zoneplate：4K→1080p 混叠 −6dB、与 ffmpeg lanczos RMS −20%。
4. 色带：8bit 渐变平台长度 ≤6px（现有 5px 保持不退化），deband 升级后台阶数 −50%。
5. 帧耗时：理想路径（1080p SDR 无 VSR）p99 <1.2ms（历史 0.75ms 均）；**现场同配置（1440p+滤镜+VSR）见 §6.2 目标：上传+渲染 p50 ≤6ms、VSR ≤3ms**；4K 无 VSR p99 <4ms。
6. 色彩：BT.601/709/2020 与 full/limited 组合 × ΔE<1；广色域屏 P3 输出 ΔE<2。
7. 稳定性：改后连续 2 小时 4K HDR 播放 + 分辨率切换 30 次 + HDR 开关 50 次，无设备丢失/花屏/崩溃。

### 4.3 音频链路（A 系列）

#### 4.3.1 三颗 P0 的落地改法（合计 1.5 天，低风险）

**① 24bit → 24-in-32（A0-5）**
- 候选改为 `{float32, int32, 24-in-32, int16}`：`wBitsPerSample=32`、`wValidBitsPerSample=24`、`nBlockAlign=ch*4`、`outBytes=4`；写入 `((int32_t*)p)[k] = (int32_t)lrintf(clamp(s,-1,1)*2147483647.0f) & 0xFFFFFF00`（左对齐 24 位）。或最简单：**删掉 24 候选**（设备要么接受 32f/32i，要么 16i）。**验收**：24bit 设备独占 60s 无异常；32i 路径 null test 残余 0。
**② int16 钳位 + TPDF + 舍入（A0-6）**
- `float s = clamp(tmp*gain, -1, 1); int32_t v = lrintf(s*32767.0f + dither)`（TPDF ±1LSB 抖动），再写 short。音量>1.0 时加 5ms look-ahead 限幅（简单峰值检测）。**验收**：200% 音量播 0dBFS 测试音无越界样本；−1dBFS 正弦 THD+N < −95dB。
**③ seek 冲刷设备缓冲（A0-7）**
- 渲染循环把 `if (devFlush.exchange(false)) { }` 改为：`ac->Stop(); ac->Reset(); ac->Start();` + 重置 `lastPad/devSamples/devMediaUs/framesOut`（照 `wasapi_sink.cpp:204-212` 的写法）；配合淡入。**验收**：20 次随机 seek，`audio_dump.f32` 在目标前 50ms 内无旧内容；欠载 0；时钟锚偏差 <5ms。

#### 4.3.2 欠载根因链（A1-21/A1-24，合计 3~4 天）

现状：渲染线程 `sleep_for(2ms)` 实际 15.6ms（代码自己在 `:369-372` 认了），独占缓冲 20ms/共享 ~10ms → 余量极小；同线程还要 `av_read_frame`（阻塞 IO）+ `dsh_log`（每条 fopen/fclose）。

改法（按顺序做，每步都可单独验证）：
1. `timeBeginPeriod(1)` + `AvSetMmThreadCharacteristicsW(L"Audio")` + `SetThreadPriority(THREAD_PRIORITY_TIME_CRITICAL)`（1 小时级改动，最大收益）。
2. 事件驱动：独占已 `SetEventHandle`（`:821`），改 `WaitForSingleObject(ev, 100)` 等设备事件（共享模式加 `AUDCLNT_STREAMFLAGS_EVENTCALLBACK` + `SetEventHandle`）；先写 20 行探针证实不会"卡死渲染线程"（历史注释说会卡，需排除当时 COM 单元/Start 顺序问题）。
3. 把 `decodeStep` 从渲染循环拆出到**独立解码线程**（环写端已加锁 `:267-301`，可复用；历史上失败的根因是 v2 架构没自开 demuxer，现在已自开）。
4. 日志改内存队列 + 单写线程（与 Q1-45 合并）。
**验收**：0.5/1/2/4× 各 60 秒欠载 **0 次**；共享端到端延迟 ~40→~25ms（IAudioClock 测）；渲染线程单轮 p99 <2ms。

#### 4.3.3 设备与独占（A1-22/A1-23，合计 3 天）

- **A1-22 设备丢失/切换**（2 天）：判 `AUDCLNT_E_DEVICE_INVALIDATED`（`GetCurrentPadding/GetBuffer` 返回）→ 置 `needReopen`，渲染线程内 `Stop/Release/Activate/Initialize` 重建（保留环内未播数据、重锚时钟、淡入）；注册 `IMMNotificationClient` 监听默认端点变更/拔出/格式变更；失败退避 + 日志 + UI 提示"音频设备已切换"。

|---|---|---|---|
| 时间轴偏移（音字幕不同步） | 控制条加「字幕延迟 ±」按钮（0.1s 步进，快捷键 `[`/`]`）+ 记忆 | 0.5 天 | 高（最常见） |
| 内嵌字幕轨 | 引擎 `LoadMedia` 找 `AVMEDIA_TYPE_SUBTITLE` 解码为事件表（老线已验证 mov_text/ASS 解析），前端选轨 | 1 天 | 高 |
| 字幕样式 | 字号/颜色/描边/底部边距设置（现在只有开关/语言） | 0.5 天 | 中 |
| ASS 特效（卡拉OK/定位） | 集成 libass（MinGW 可编，依赖 freetype/fribidi/harfbuzz），渲染 RGBA 上传纹理叠加 | 2~3 天 | 中 |
| PGS/SUP 图形字幕 | FFmpeg 解 `AVSubtitle` 位图 → 上传纹理；与 libass 共用叠加层 | 1~2 天 | 低 |
| AI 字幕改进 | 已有链路；可加 VAD 自动校时、跳过片头片尾 | 1 天 | 中 |

**验收**：ASS 特效字幕（卡拉OK）颜色/定位/淡入淡出正确；PGS 蓝光字幕能显示图片字幕；时间轴偏移 ±10s 内即时生效并记忆；内嵌多字幕轨可切换。

- 首页/列表：1000 条视频滚动不卡（虚拟化）；首页首次 P95 <50ms。

- 日志可查：任意故障能用"日志 + 关于页版本 + diag.ps1"三件套定位。

### 6.7 验收流程（每个改动都走）

1. **改前留基线**：截图/短视频、PSNR/帧耗时/日志行数、`DshEngine_GetStats` 快照（做完 Q1-46 后）。

4. **看现场日志**：`dsh_engine.log` 的 `[性能]`/`seek->show`/`DM: TICK`/`音频[循环]` 对比改前。
5. **用户实机验收**：白屏/4K/耳机插拔/长时间播放这几类必须真机跑（用户自己会测）。

## 7. 风险与回滚策略

### 7.1 高风险改动（每项都必须带"回滚开关 + 验证门槛 + 最小步数"）

| 改动 | 风险 | 回滚开关 | 验证门槛 | 最小步数 |
|---|---|---|---|---|
| Vulkan 单提交 + 多帧 in-flight（R1-9） | 花屏/黑帧/设备丢失（同步错误） | `DSH_VK_SYNC=legacy` | SDR/色调映射/直通三模式逐字节 A/B；30 分钟压力 + 分辨率切换 50 次不掉设备 | ①upload+render 合并成单提交（仍全同步）→②in-flight=2 →③跨 API semaphore |
| 跨 API 信号量/fence 替代全同步 | 撕裂/卡死/驱动兼容 | 同上 | 120Hz 播放 30 分钟 + 全屏切换/窗口缩放；GPU 帧延迟测 | 先写独立探针验证 D3D11Fence 共享句柄可被 Vulkan 等待 |
| HDR 线性光滤波（R0-14） | 色调/亮度变化、性能下降 | `DSH_HDR_LINEAR=0`（默认开） | 同帧 A/B 高光误差 <5%；HDR→SDR PSNR 不降；直通逐字节不变 | 先只改 `filterScale`，再改 `filterDeband` |
| 缩放核替换（R0-15） | 锐度观感变化、性能 | `DSH_QUALITY` 旧档位保留 | zoneplate 混叠 −6dB；4K→1080p 参考 RMS −20%；帧耗时 +≤1ms | 先 box 止血 → 再 8-tap 带限 → 再放大档 |
| 帧队列背压（E0-2） | 低（一行改动） | 无（直接回滚 commit） | 4K 播放 N≈M、seek 恢复、无新卡顿 | 一次改完 |
| 请求优先级（E0-3） | 换片失败率 | 保留旧单槽路径开关 `DSH_REQ_LEGACY=1` | 100 次"打开+立刻 seek"无黑屏 | 先 CAS 最小改 → 再 4 槽环 |
| LoadMedia/DoSeek2 缩锁（E1-1） | 竞态/崩溃（锁语义变了） | `DSH_LOCK_LITE=0` | 100 次换片 + 1000 次 seek 压测；UI 无冻结；帧队列无重复/丢帧 | 先把 open 移出锁 → 再移 seek → 每步压测 |
| D3D 资源单线程化（E1-4） | use-after-free/黑屏 | 开关回旧路径 | `DSH_TEST_DEVICE_LOST=flap` + 换片 100 次不崩 | 先加 `g_gfxMtx` 兜住 → 再改创建线程 |
| 音频线程拆分/事件驱动（A1-21/A1-24） | 静音/欠载变多/卡死（历史踩过） | `DSH_AUDIO_LEGACY=1`（回到 2ms 轮询 + 同线程解码） | 0.5/1/2/4× 各 60s 欠载 0；端到端延迟测得下降；无卡死 | ①MMCSS/timer →②事件驱动 →③解码线程拆出（逐步验证） |
| 硬解零拷贝（R1-16） | 崩溃/绿屏/花屏/驱动兼容 | `DSH_HWACCEL=none`（默认软解） | 与软解逐帧 PSNR ≥45dB；4K 2 小时；切分辨率/切 HDR 不崩 | 先独立探针通全链路 → 再按"仅 4K/仅 HEVC"灰度 |
| libass 集成（字幕） | 构建依赖/字体/性能 | 字幕设置可选"内置解析器" | ASS 特效测试集正确；不掉帧 | 先静态库编通 → 再接渲染层 |
| 在线直链播放（4.6.5） | 直链时效/版权/风控 | 功能默认关闭（设置项） | 起播 <2s、seek 行为符合预期、失败有明确提示 | 先做 A 方案（缓存+Range），B 方案单独立项 |
| 设备丢失重建逻辑改动 | 重建风暴/蓝屏 | 保留现有双阀 + 自测钩子 | `1/dead/flap` 三档自测通过；60s 内 ≤3 次 | 任何改动都必须先跑三档自测 |
| 音频 24-in-32 / int16 钳位 | 低 | 回滚 commit | 24bit 设备 60s、null test、THD | 一次改完 |
| 后端 token/路径白名单 | 旧前端不兼容（403） | token 校验可临时关（配置项） | 新旧前端都能跑；越界 403；正常接口不受影响 | 先加白名单 → 再加 token（分两步发版） |

### 7.2 通用纪律（延续 `docs/工程纪律.md`）

1. **一次只改一个变量**，保留 env/设置开关；热点路径（Present/音频循环/弹幕 Tick）改动必须 A/B。
2. **改前留证**：截图/短视频、PSNR/帧耗时、日志行数、`GetStats` 快照；改后同条件再测。
3. **版本三方对齐**：源码 vs `bin` vs 安装目录的 exe/dll MD5 必须一致（看日志第一行 build info）。
4. **部署纪律**：`deploy.ps1` 是唯一交付方式；不要用 `dotnet build -t:Rebuild` 对交付目录动手；部署前确认播放器没在跑（脚本已拦）。
5. **不删用户数据**：`data/`、`extensions/`、书库/视频库只迁移不清理。
6. **文档跟代码走**：弹幕三份文档、HANDOVER、CHANGELOG 每轮同步；老线文档归档别混用。
7. **设备丢失类改动**必须先跑 `DSH_TEST_DEVICE_LOST=1/dead/flap` 三档自测（这是历史上唯一把机器拖蓝屏的方向）。
8. **用户实机验收**：白屏、4K、耳机插拔、长时间播放四类必须真机跑一遍再宣布完成。

### 7.3 需要用户决策 / 实机配合的事项

1. **4K 实测**：本会话不能启动播放器，E0-2（背压）对 4K 的实际影响需要用户播一段 4K 视频观察（或看修复前后的日志 `[性能]`/`seek->show`）。
2. **在线直链播放优先级**：这是产品级能力（3~8 天），是否排在"画质/硬解"之前，需要用户定。
3. **硬解与画质优先级**：如果用户更在意 CPU/功耗/风扇，硬解（R1-16）应提前；如果更在意画面，先做缩放核/LUT。
4. **色彩管理**：是否需要针对某台显示器做 ICC 校色（需要用户提供 `.icc` 文件），是否需要 P3 输出。
5. **字幕 libass**：是否接受安装包 +2MB 左右、依赖 freetype/fribidi/harfbuzz；若不接受就只做"时间轴偏移 + 内嵌轨"。
6. **默认值调整**：HDR tone boost、deband 强度、弹幕默认透明度/速度、RTX VSR 默认开关是否要改默认。
7. **白屏复现**：若再出现，请用新版 `diag.ps1` 抓现场（新版本会把 build info/GetStats/渲染路径写进诊断包）。

### 7.4 本文档的局限

- 以**只读静态审计**为主：未启动播放器/后端，除标注"现场日志实测"的数字外，ms/带宽/内存均为推算，需实测复核。
- 现场日志跨天拼接且两份主日志**没有日期**（引擎是开机毫秒、前端是时分秒），"音轨 EOF → 假结束"的因果链只能靠内容巧合对齐（237s 与 pos=235633 吻合）；但 **37 次循环本身与音轨 EOF 本身是确凿的**，修复后用测试片可确定性验证。
- `DEVICE_REMOVED / 0x887A0005 / 设备丢失` 在现有日志中出现 **0 次**——"41 次重建风暴/整机蓝屏"无法从这批日志证实；只能看到 Init 风暴前兆。历史结论仍以 CHANGELOG 为准。
- 0.25 倍速在这批日志里**从未出现**（只有 0.50x/1.00x），"0.25x 欠载 27 次"不予作为本次结论。
- 老线（`_legacy-player`）代码未审，只作为"可移植参考"提及；EPUB/PDF 扩展、AI 增强器内部实现不在本方案范围。
