# 璃鸢镜 · 第二轮现场问题调查与修复方案（2026-10-31）

> **背景**：第一轮审计后落地了 Top3 优化（分支 `opt/player-top3`，已装到用户机器）。用户在真实使用中报了 5 个问题：

> **本轮做了什么**：4 路并行子审计 + 主审计员复核，全部以**用户机器上的真实运行日志**（截至 2026-10-31 18:36，`dsh_engine.log` 60,561 行 / `dm_debug.log` 85,687 行）与当前源码为依据。**只读调查，没有改任何源码/安装目录**。
> 现场版本已核对：引擎 `dsh_engine.dll` SHA256=`405A7778FE55814E…`、界面 `WinUIGui.dll` SHA256=`1C9B8B4587D8188B…`，分别与工作区 Top3 引擎构建、`D:\Temp\lyra_host_top3_build` 逐字节一致 → **跑的就是本仓库源码**，日志结论可直接对应到代码行。

## 0. 一页速览

| # | 问题 | 根因（一句话） | 修复面 | 推荐优先级 | 估算 |
|---|---|---|---|---|---|
| 1 | 切画质概率「未响应」 | **RTX VSR 的 NGX 特性在 UI 线程的 `Present()` 里被销毁重建**（每次切换 366~422ms），撞上上一代 VSR 的 GPU 工作在飞 → **TDR（DEVICE_HUNG）**，`Present` 内 Vulkan fence 等待又是 **5s 无界**，单次卡 5.26s → Windows 判未响应 | 引擎为主（VSR 生命周期/等待上界/缩锁） | **P0** | 止血 0.5 天 / 正解 2~3 天 |
| 2 | 切画质闪「开头一帧」 | `LoadMedia` 从 0 出帧，前端要等 `GetDurationMs()>0` 轮询才 `SeekJump` → 开头画面曝光 **445~476ms**（TDR 那次 5.42s）；seek 后还会先闪落点前 2.2~3.6s 的旧画面 50~100ms | 引擎加 `OpenMediaAt(path,startMs)` + 前端删轮询 | **P0** | 0.5~1 天（止血 20 行） |
| 3 | 加载时间长 + 启动后必卡一次 | 每打开一次视频就把引擎**整个 Shutdown→Init 重装**，重装时无条件让引擎重新探测 NVNGX：**453~718ms（p50 609，占打开耗时 60~80%）**；且 `ApplyRtxVsrOnOpen` 在媒体未加载时必然失败（14/14 全 -5）→ 1.2s 后在 UI 线程重试 → **Rv_Init + VSR 首帧冻结 438~672ms**（100% 复现，因为用户开着 VSR） | 前端只准备一次 SDK + 引擎 VSR 初始化移出 UI 线程（与 #1 同一改动） | **P0** | 1~2 天 |
| 4 | 关闭扩展页面慢 | 关闭是「先取消 → 等扩展 finalize 回执 → 再第二次 Close」，**PDF 扩展 0.3.0 根本没实现 finalize** → 每次关 PDF 恒定吃满 **1500ms 超时**；窗口在等待期一直可见 | 宿主 `ExtensionHostWindow` + PDF 扩展 | **P1** | 快赢 1.5h / 完整 6~7h |
| 5 | EPUB 目录序号左溢出 | 0.6.1 目录项没有独立序号元素：看到的"序号"是标题开头"第N章"或**书内目录页 `<ol>` 标记**。① 全局 `button{white-space:nowrap}` 让长目录项不换行 → 侧栏横向可滚 435px>271px，横滑后整列左移、开头序号被切；② 书内 `<ol>` 默认 `outside` + `padding-left:1.5em`(33px) 装不下"100."(44px) → 被 `overflow:hidden` 裁掉 | 扩展 CSS 3 处 + 可选 grid 序号列（需发 0.6.2） | **P1** | 0.5 天（含回归） |

**当天可上的止血包（约 1.5~2 小时改动，风险低）**
1. 切画质期间临时 `DshEngine_SetRtxVsr(0)`，切完 seek 完成再恢复原值（只改内存开关，不写配置）——消掉 #1 的 0.37s 卡与 TDR 路径的触发条件。
2. 切画质点击时立刻在视频层盖不透明遮罩（或保留旧帧），`SeekJump` 完成 300ms 后撤——用户看不到开头帧（#2 观感）。
3. **NVNGX 探测降为每进程一次**：前端加实例级 static 记住"SDK 目录 + DLL 文件大小/时间戳"，未变就跳过 `CopyRtxDllsToApp` 与 `SetRtxSdkPath("")`；引擎 `SetRtxSdkPath` 在空路径且已无自定义目录时提前返回缓存值——每次开视频快 ~0.45~0.7s（#3 的三分之二）。
4. `ExtensionHostWindow` 收到关闭请求后先 `AppWindow.Hide()` 再做 finalize，超时 1500→250ms，并对"从未发过 v3 协议"的旧扩展（PDF）免等待——关闭感知 <100ms（#4）。
5. EPUB 扩展最小 CSS：`.toc-item{white-space:normal}`、`.side-scroll{overflow-x:clip}`、`#lyra-content ul/ol{padding-left:2.6em}`（#5，需发 0.6.2）。

> 结论先行：**#1/#2/#3 是同一个技术债的三个面——"RTX VSR 生命周期和 GPU 等待都放在 UI 线程的 Present 里"**。把 VSR 的初始化/销毁挪出 UI 线程、给所有 GPU 等待加上界、加载即定位（OpenMediaAt），三个问题一起收；否则单修任何一个都只是止血。
> 另外 #3 的"加载慢"还有一个结构性问题：**每打开一个视频都新建 VideoWindow、把引擎 Shutdown→Init 重装**（37 次打开对应 37 次 Init），其中无条件重探 NVNGX 占打开耗时 60~80%——不解决"复用窗口/引擎"，其它优化都只能省小头。

## 2. 问题一：切换画质概率性「未响应」

### 2.1 现场时间线（18:33:30.272，1080P → 480P，一次真实卡死）

| 时刻 | 证据 | 内容 |
|---|---|---|
| 30.272 | `dm_debug.log:85457` | `切换画质 → 480P（位置 3833ms，暂停=False）` |
| 30.277~30.333 | dm L85458-85469 | OpenMedia 同步段（字幕/音量/画质版本/META）≈18ms，**不是卡点** |
| 30.355 | `dsh_engine.log:60251`（tick 258823531） | `LoadMedia ok 852x480`（加载本身 ~63ms） |
| 30.745 | engine L60253（tick 258823921） | `RTX VSR: 已初始化 852x480 → 2787x1570`（**VSR 特性重建完成**；从 LoadMedia ok 到这里的 ≈390ms 就是 `Rv_Shutdown+Rv_Init`，三次切换量级 366~422ms） |
| 30.379→35.79 | dm 43 条 TICK 缺失 | **UI 线程停摆 5.4s**；35.636 引擎打出 `Present 设备丢失 hr=0x887A0005 reason=0x887A0006`（DEVICE_HUNG/TDR） |
| 35.777 | engine L60273 | `★ 设备已重建`（141ms） |
| 35.791 | dm L85471 | `切换画质完成`（此刻才发 SeekJump(3833)） |
| 35.806 | dm L85476 | `★ C# 渲染回调停摆：已 5.4 秒没触发 OnRenderFrame`（第二重证据） |
| 36.541 | dm | TICK 恢复：pos=3900（已回目标位） |

第 2、3 次切换（40.79→41.36、42.74→43.21）没有 TDR，但仍有 **0.45~0.48s** 的 UI 卡顿（同样来自 VSR 重建，实测 422/375ms）。

### 2.2 根因链（按证据强度）

1. **【确凿】VSR 特性在 `Present()` 里销毁重建**：`dsh_engine.cpp:2641-2644` 每帧调 `vsr_process_cpu()` → `vsr_prepare()`（`:543-552`）。源分辨率一变（1080P→480P，VSR 目标 3840×2160→2787×1570），就 `vsr_release_feature()`（`:515-518`，`Rv_Shutdown` 无日志）+ `Rv_Init`（`:545-552`）。三次切换实测重建耗时 **366 / 422 / 375 ms**——**全部在 UI 线程上**。
2. **【确凿】`Present()` 内的 GPU 等待无界**：`vulkan_video.h:499` 的 `WaitForFences(..., 5s)`（超时后还不复位 fence）；`:318/:415`（另有 `:253`）的 `vkQueueWaitIdle()` **没有超时**（`:405` 是它的定义）。这些都在 UI 线程。
3. **【确凿】TDR 的直接证据**：上一次 4K VSR 的 GPU 工作还没落地就 `Rv_Shutdown`+重建 → 驱动 TDR（`DEVICE_HUNG`）→ `Present` 卡 **5.257s**（与 5s fence 同量级）→ 重建 141ms → 合计 **5.41s** → Windows 判「未响应」。
4. **【推断】为什么是"概率"**：卡不卡取决于切换瞬间 GPU 队列里是否还有上一代 VSR 的工作在飞。从高画质（4K VSR 输出）切到低画质时最容易撞上；第 2/3 次输出更小或 GPU 已空闲，就只慢半秒。
5. **【确凿】第二条潜在卡死路径（本次未触发）**：`Present()` 用阻塞 `lock_guard(g_mtx)`（`dsh_engine.cpp:2599/2619`），而 `LoadMedia()` 全程持锁（`:2033`），锁内含 `avformat_open_input/find_stream_info/avcodec_open2` 和 `g_audio.openFile()`（`:2071`；`audio_out.h:155` 有 `i<400 sleep(10ms)` 等设备就绪，**最多 4s**）。独占模式/设备被占用时就是现成的 4s 卡死。

### 2.3 修复方案

**① 止血（当天，0.5 天）**：切画质期间临时关闭 VSR。
- 前端 `SwitchQualityAsync`（`VideoWindow.xaml.cs:2976`）：开始时 `bool vsr = _rtxVsr; if (vsr) DshNative.DshEngine_SetRtxVsr(0);`，`SeekJump` 完成后再 `SetRtxVsr(1)`（`SetRtxVsr(0)` 只置标志 + `Rv_Shutdown`，不重建；恢复时的 `Rv_Init` 在目标尺寸确定后只做一次，且此时没有在飞的旧帧）。
- 或引擎加环境变量 `DSH_VSR_SAFE_SWITCH=1` 走同样逻辑，前端不用改。
- 预期：切换时不再触发 TDR（关掉 VSR 就没有"旧 VSR 工作在飞"），但仍会慢 ~0.3s（VSR 重建挪到 seek 后）——配合 ② 的遮罩，用户不可感。

**② 正解一：把 VSR 生命周期移出 `Present()`（1.5 天，与问题三共用）**
- `vsr_prepare()` 只允许在**解码线程**或专用 VSR 工作线程调用；`Present` 只读 `g_vsr.ready/outW/outH`，遇到"目标尺寸已变但未就绪"时**跳过该帧 VSR**（走不超分直通路径），下一帧用新特性。
- 换片/换分辨率时 `g_vsr.suspended=true`，`LoadMedia` 完成后由解码线程按新目标尺寸 `Rv_Init` 一次，成功后清 suspended；`Present` 不阻塞。
- 风险：`Rv_Init`/`Rv_Shutdown` 在非 UI 线程调用需要验证 bridge 的 D3D11 多线程保护（`ID3D11Device` 本身线程安全，`ID3D11DeviceContext` 不线程安全——bridge 内部用自己的 context，需加锁串行化）。

**③ 正解二：`Present` 内所有等待加界（0.5 天）**
- `vulkan_video.h:499`：5s → **100ms**；超时 `ResetFences` + 计失败，连续 3 次失败本帧起回退 D3D11 并写日志（不得静默）。
- `:318/:415`（另有 `:253`）的 `vkQueueWaitIdle()`：尺寸变化分支改为"不等待，标记重建、本帧跳过"。
- 加 `[性能] Present 分段耗时`（VSR 准备/回读/上传/渲染/Present 各一段，>100ms 必打）——先有数据再优化下一轮。

**④ 正解三：`Present` 改 `try_lock` + `LoadMedia` 缩锁（2~3 天）**
- `Present` 的 `lock_guard` → `unique_lock(..., try_to_lock)`：拿不到本拍跳过（下帧再来），UI 永不被解码线程锁死。
- `LoadMedia` 把 `avformat_open_input/find_stream_info/avcodec_open2` 与 `g_audio.openFile` 挪出 `g_mtx`，锁内只做指针交换/状态复位（<1ms）。FFmpeg 打开过程的线程安全需单独验证（先只挪 openFile，它是 4s 卡死的最大头）。

### 2.4 验收（切 20 次，含 1080P↔480P↔4K 交替）

1. 无 `★ Present 设备丢失`、无 `★ C# 渲染回调停摆`。
2. 单次 `Present` 分段日志 <100ms；切画质期间最长 TICK 间隔 <200ms。
3. `SwitchQualityAsync` 从点击到 `切换画质完成` <400ms（现在 TDR 那次 5.52s、正常 0.48~0.57s）。
4. 切完第一条 TICK 的 pos 与原位置差 ≤±200ms。

### 2.5 风险与回滚

- ABI 若要升（见问题二）必须"引擎 DLL + 主程序"成对发布，旧 DLL 会被 `_engineApiMismatch` 判出（`VideoWindow.xaml.cs:347-358`）。
- VSR 改线程：回滚开关 `DSH_VSR_SYNC=1`（走旧路径）。
- 等待加界：回滚 `DSH_VK_WAIT_MS=5000`。
- 缩锁：回滚 `DSH_LOCK_FULL=1`。

## 3. 问题二：切换画质闪「开头一帧」

### 3.1 现场证据

- 新文件从 **0 出帧**：`LoadMedia` 末尾 `lastPtsUs=0`（`dsh_engine.cpp:2085`）、主时钟显式锚定 0（`:2114`）、`mediaLoaded=true`（`:2115`）；前端这时还在轮询回位（`VideoWindow.xaml.cs:2986-2991`：`for(60){await Task.Delay(100); if(GetDurationMs()>0) break;}`）→ 引擎日志与前端 TICK 对齐后，**开头画面曝光 445 / 476 ms**（≈片头 11 帧 @24fps）；TDR 那次被放大到 **5.42s**（`TICK pos=29` 后直接 5.4s 空档）。
- **seek 后还会闪一帧"更早"的内容**：`DoSeek2` 置 `queueFirstAfterSeek=true`（`:2159`），`DecodeAhead` 对落点关键帧跳过判据、先入队上屏（`:2239-2247`）。日志：目标 7267ms→落点 5033ms（差 2234ms）、目标 8600ms→落点 5033ms（差 3567ms），随后才「追赶 67/107 帧、45~57ms」——即回位后先看到 2.2~3.6s 前的内容约 50~100ms。

### 3.2 修复方案

**主修（0.5~1 天）：`DshEngine_OpenMediaAt(path, startMs)`——加载内定位 + 不曝光落点前的帧**
1. 引擎新增导出：`DshEngine_OpenMediaAt(const wchar_t* path, int64_t startMs)`；`DshEngine_GetApiVersion` 返回 **3**；前端 `ExpectedEngineApiVersion` 同步改 3（旧版回退旧轮询路径）。
2. `LoadMedia()` 末尾（`g_mediaLoaded=true` 之前）若 `startMs>0`：`avformat_seek_file` + `avcodec_flush_buffers` + `g_qCount=0` + `g_originPts=startMs` + `lastPtsUs=startMs` + `dsh_clock_anchor_to(startMs)` + `g.skipsToClock=true` + **`g.queueFirstAfterSeek=false`** + `g_audio.flush(startMs)`；`startMs` clamp 到 `[0, dur-1000]`（各画质时长可能差几百 ms）。
3. `Present()` 弹帧后：若"起始位置尚未达成"→ 丢弃该帧、不上传、不 render；**Vulkan 目标纹理保留上一画质的最后一帧**（D3D11 路径沿用 `lastFrame+needReupload`）→ 肉眼是"旧画面停 ~100~300ms"，而不是"闪开头"。
4. 前端 `SwitchQualityAsync` 改调 `OpenMediaAt(path, pos)`，删掉 6s 轮询；`SetPaused(wasPaused)` 保留。`OpenMedia(path)` 加默认 `startMs=0` 重载。
- 验收：切 20 次，① `LoadMedia ok` 后 3 行内必须出现 `seek jump`，且不出现"落点 0ms"；② 每次切完第一条 TICK 的 pos 与原位置差 ≤±200ms，绝不出现 `pos<1000`；③ 眼视无开头帧；④ 切画质耗时从 0.48~0.57s 降到 <400ms。

**前端止血（20 行，当天）**：点击画质时立刻在视频层盖一块不透明 `Grid`（或冻结最后一帧），`SeekJump` 后 300ms 淡出；同时禁用画质按钮防连点。

**附带修复**：`SwitchQualityAsync` 加 `_mediaGen` 代次校验（每次 `await` 回来 `if (gen != _mediaGen) return;`），避免连点两次画质时把 A 的 seek 打到 B 上。

### 3.3 风险与回滚

- `LoadMedia` 内 seek 会让首帧晚 50~150ms（日志实测追赶 45~57ms；4K 长 GOP 可能 300~600ms）；用"保持上一帧"掩盖，并保留 `DSH_SEEK_FAST=1` 兜底。
- ABI 3 与前端强校验：必须成对发布；回滚则前端 fallback 到旧轮询路径。

**结论（修正上一版判断）：加载慢的主因不是解码、也不是 DLL 复制，而是「每次打开视频都把引擎整个拆了重装，重装时无条件重新探测 NVNGX」**（占 60~80%）；其次是 Vulkan 首建（~15%，仅进程首开）、弹幕层重复重建（~5%）、Init（~5%）。DLL 复制实测只有 **11.4ms（9.2+2.2）**，**不是主因**（之前按 23MB 估算过大了）；但它有两个隐患：①DLL 已被进程加载后覆盖会抛 sharing violation，被 `catch { return false; }` 静默吞掉，而日志不管成败都打"已复制"；②真正贵的是它后面的 `SetRtxSdkPath("")`。
**结构性根源**：`MainWindow.xaml.cs:113-117` 视频窗 `Closed` 即置 `_video=null`，下次点播**新建 VideoWindow** → 每次都要重付 Init + NVNGX 探测 + Vulkan 首建 + 3 次 D3DCompile + 64MB 图集（日志里 37 次 `窗口尺寸` 对应 37 次 `Init ok`、44 次 LoadMedia 中 37 次前面带 Init）。

### 4.2 「启动后几帧必有一次卡顿」——VSR 首次初始化在 UI 线程，438~672ms

| 打开 | 首次尝试 | 重试触发 → 返回 | UI 冻结 |
|---|---|---|---|
| 第 1 个视频 | 18:36:08.913 `ApplyRtxVsrOnOpen 首次失败 rc=-5 → 1.2 秒后重试` | 10.113 → 10.514 | **≈585ms**（TICK 10.015→10.600） |
| 第 2 个视频 | 18:36:14.569 同样 rc=-5 | 15.769 → 16.434 | **≈668ms**（TICK 15.766→16.434，缺 5 个 TICK） |
| 统计 | `首次失败 rc=-5`：**14 次、全是 -5、零例外** | 引擎 `RTX VSR: 已初始化` 前一行的空档：**p50 438 / max 672 / n=20**（期间零日志） | — |

机制（5 步闭环）：
1. **首次 `SetRtxVsr` 必失败**：`DshEngine_OpenMedia` 只是投递请求立即返回（`dsh_engine.cpp:1505-1516`），前端同一线程下一行就调 `ApplyRtxVsrOnOpen()`（`VideoWindow.xaml.cs:5496→5501`）。此刻 `g.vw/g.vh=0` → `vsr_calc_target` 首行 `return false`（`:520`）→ `vsr_prepare` 返回 false（`:541-542`）→ `SetRtxVsr` 返回 **-5**。
2. **重试落在 UI 线程**：`_ = RetryRtxVsrOnOpenAsync(1)`（`:681`）里的 `await Task.Delay(1200)` **没加 `ConfigureAwait(false)`**（`:703`）→ 续体回到 UI 线程，紧接着在 UI 线程调 `DshEngine_SetRtxVsr(1)`（`:706`）。
3. **该调用里做 NGX 实例 + 4K 输出纹理**：`vsr_prepare()` → `pInit(g.dev, 3840, 2160)` + 取输出 SRV（`dsh_engine.cpp:545-550`），之后还会"立刻把最后一帧跑一遍 VSR"（`:2531-2535`）→ 引擎日志实测空档 **438~672ms**（期间零日志）。
4. **前端心跳空洞正好包住它**：TICK 是 125ms 定时器；实测 585/668ms 空洞内正含 `延迟重试开启成功` 那一行 → 双证 UI 线程被冻结。
5. **因为用户设置里 `rtx_vsr=true`，所以每次打开视频都必然发生一次**——这就是"启动后几帧必有一次卡顿"。

已排除（02 报告附带证据）：`ensure_vk_target` 首建 141ms（发生在 `LoadMedia ok` 后 +187ms，比卡顿早约 1.2s，不重合）；`create_danmaku_layer` 首建 15~31ms；Top3 的 qCap 320MB/帧队列（`DecodeAhead` 有真背压、1080p cap≈40 帧、`[性能]` 无尖峰）。

## 5. 问题四：关闭扩展页面耗时较长

### 5.1 关闭时序（现状）

```
用户点 ✕ / Alt+F4
  → AppWindow.Closing                ExtensionHostWindow.xaml.cs:566 起
  → args.Cancel = true               :570   ← 先吞掉本次关闭（窗口继续显示）
  → PostWebMessage "host.finalize"   :573-575
  → 起 1500ms 超时定时器             :578
  → 等扩展回 "host.finalized"        :300-310（收到 → FinishFinalizeAndClose）
  → FinishFinalizeAndClose           :581-590 → Close()
  → Closed → CleanupTemp()           :88 → :658 Directory.Delete(_tempDir, true)（同步 UI 线程）
```

**窗口在整个等待期一直停在屏幕上** → 等待 1.5s 就是肉眼 1.5s 卡顿。

### 5.2 根因

1. **【确凿】PDF 扩展 0.3.0 没有实现 `host.finalize`**：`extensions\pdf\reader.js` 全文只有 1 处 `postMessage({type:"lyra-book-ready"})`（第 23 行），无 message 监听 → 回执永不到 → **每次关 PDF 恒定吃满 1500ms**。
2. **【确凿】EPUB 稳态很快，但有最坏 4.3s 路径**：`reader.js:1850-1863` 三个 `bounded(2800ms)` + 1200ms；`:1814` `if (state.finalizing) return;` 提前返回时不发回执 → 必定等满超时。历史 `final-host-debug.log` 实测 CLOSING→CLOSE_ACK 稳态 1/8/2ms（6 组），说明慢主要在 PDF/异常路径。
3. **【确凿】清理在关闭路径上同步跑 UI 线程且失败**：WebView2 仍持有目录映射 → `Directory.Delete` 抛异常被 `catch` 吞掉、`_tempDir=null` 永不重试。实测 `D:\Temp\lyra_ext_host` 残留 **102 个目录 / 3,614 个文件 / 295MB**（10-30 20:30 仍在生成）。

已排除：`ReaderStateStore` 纯本地文件、不走 HTTP；没有 `Task.Wait/GetAwaiter().GetResult()`；MainWindow 没有 `EnableWindow` 冻结。

## 6. 问题五：EPUB 目录左侧序号从左侧溢出

### 6.1 先澄清"序号"是什么

安装中的 EPUB 扩展是 **v0.6.1**（与仓库 tag `v0.6.1` 逐字节一致）。它的侧栏目录 `buildTocList`（`reader.js:628-635`）只创建一个 `<button class="toc-item">`，内容是"▾ + 标题纯文本"——**没有独立的序号元素**；`reader.css:39-44` 里也没有 `counter/::before`。所以用户看到的"左侧序号"只可能是：

- **A. 章节标题开头的"第N章"**（侧栏目录项），或
- **B. 书内目录页的 `<ol>` 列表编号**（正文里由分页器渲染）。

两种情况都已在 Chromium 里复现出"从左侧溢出/被裁"。

### 6.2 根因（两条都确凿复现）

**A. 侧栏：全局 `button{white-space:nowrap}` 导致长目录项不换行 → 横向溢出 → 横移后开头序号被切**
- `reader.css:20`：全局 `button { … white-space:nowrap; }`；`.toc-item`（`:39`）虽然是 `<button>` 但没有复位 `white-space`，于是 `overflow-wrap:anywhere` 失效、长标题不换行。
- 实测（280px 侧栏、40 条长标题）：`.side-scroll`（`:36`）`clientWidth=271 / scrollWidth=435`，可横向滚约 156px；单条目 `clientWidth=255 / scrollWidth=379~443`。
- 触发：触控板横滑 / Shift+滚轮 / 拖选自动滚动把 `scrollLeft` 推大后，`updateTocActive()` 的 `box.scrollTo({top})`（`reader.js:651`）**不会复位水平位置**（实测设 180 后仍保持 156）；`overflow-x:hidden` 又不显示滚动条，用户察觉不到。整列左移后，"第123章"开头的序号被切在左边界外——与用户描述完全一致。
- 缩进叠加：`paddingLeft = 8 + depth*16`，depth=3 时可用文字宽只剩 191px（约 14 个汉字），普通网文标题 12~25 字，深层目录几乎必溢出。

**B. 书内目录页：`<ol>` 默认 `list-style-position:outside` + `padding-left:1.5em` 装不下三位数序号**
- `paginator.js:36`：`#lyra-content ul, #lyra-content ol { margin:0 0 1em; padding-left:1.5em; }`；默认 `list-style-position:outside`，标记画在内容盒左外侧。
- 实测（Microsoft YaHei UI，22px）："1." 宽 18.2px（0.83em），"**100.**" 宽 **44px（2.0em）**；2.0em > 1.5em → "100." 左边缘落在容器内边 **−11px**，被 `html,body{overflow:hidden}`（`paginator.js:18`）裁掉，只剩 "00."。**与字号无关（em 等比）：2 位数刚够，3 位数必溢出。**
- 前提：该书的"目录"必须是正文 spine 里的一页（中文 EPUB 很常见）；若用户只在侧栏看目录，就只走 A 路径。

### 6.4 修复方案

**最小改法（只改 CSS/一行 JS，0.5 天含回归；需发 0.6.2）**

`extension/reader.css`：
```css
/* :36 切断横向滚动容器：clip 不形成滚动容器，scrollLeft 恒为 0 */
.side-scroll { overflow-x: clip; }
/* :39 之后：覆盖全局 button 的 nowrap，恢复 0.5.24 的换行 */
.toc-item { white-space: normal; }
```
`extension/paginator.js:36`：
```js
#lyra-content ul, #lyra-content ol { margin: 0 0 1em; padding-left: 2.6em; }
```
- 只改 `overflow-x:hidden` 不够：hidden 只是不显示滚动条，元素仍是横向滚动容器，`scrollLeft` 照样能被手势改写，列还是会左移；必须同时让内容不再超宽（换行）或改用 `clip`。
- `overflow-x:clip` 需 Chromium ≥90，WebView2 常青版满足；旧版退回 `hidden`。
- 影响面：目录项变多行（`updateTocActive` 用 `offsetTop`，仍正确）；正文列表缩进 +1.1em。

**稳健改法（显式序号列 + 彻底不越界，建议 0.6.3）**
- `.toc-item` 改 `display:grid; grid-template-columns:2.4em minmax(0,1fr); column-gap:6px; white-space:normal`；新增 `.toc-idx`（`text-align:right; color:var(--sub); font-variant-numeric:tabular-nums`）与 `.toc-label`（`min-width:0; overflow-wrap:anywhere`）；分组项 `grid-template-columns:1fr`。
- `reader.js:632-633`：append 两个 `span`，`.toc-idx` 用 `state.book.findSpineIndexByPath(node.path)+1`（目录节点没有现成序号字段）；分组节点不显示序号；深度仍用行内 `paddingLeft`。
- `paginator.js:36` 改 `padding-left:0; list-style-position:inside`（恢复 0.5.25 行为，任何位数/字号都不会被裁；代价是悬挂缩进消失）；要保留悬挂缩进就用 `padding-left:3em`。

宿主（主程序）不需要改动；若以后给 WebView2 设 `ZoomFactor`，只需保证 `.side-scroll` 不再产生横向溢出。
