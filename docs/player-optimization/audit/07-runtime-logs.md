## 3. 关键现场还原

**事件一：一部 3m56s 的 MV 被"结束判定"循环了 37 次（最严重）**
时间线（`dm_debug.log:12467` 起）：19:25:11 起，每隔 **3 分 57 秒**精确重复一次：`结束判定成立: pos=235633 dur=236394 nearEnd=False stalled=True` → `播放结束: 单集循环 → 重播`。`nearEnd=False` 说明距离片尾还有 761 ms，判定的唯一依据是 `stalled=True`（位置不再前进）。引擎侧给出因果链：`av_read_frame 失败 r=-541478725`（= `AVERROR_EOF`）落在 **237.0 s**，同刻 `已交设备=11361216 帧`（÷48000 = 236.69 s）、`环内=0 帧`、`RMS 0.0000`——音频样点被吃干净后再也喂不出数据，而 A/V 主时钟 `来源=音频`，于是媒体时间冻结在 235.633 s，前端看到"位置不动"就判结束。**这是"连播结束判定"与"音轨 EOF"两个缺陷叠加**：任何音轨比视频短的片子都会无限自循环，且用户看到的是"每次播到 3 分 56 秒就跳回开头"。

**事件二：10 分钟内 13 次多余 Init，113 ms 内三次建交换链（重建风暴的雏形）**
`dsh_engine.log:2465–2551`：792646875 枚举显卡→Init；随后 792710328、792710390、792710421 **连续三次**完整走完"枚举 3 块适配器 → `Init: D3D11 实际在用` → `交换链 2288x1408` → `Init ok`"，彼此间隔 62 ms / 31 ms，中间**没有任何 Shutdown**。整份日志 Init 24 次、Shutdown 仅 18 次、DLL 卸载 13 次；`2472..2980` 一段内连开 6 个引擎实例才关一次。这是"设备丢失后重建风暴乃至整机蓝屏"的同类前兆（本次未升级为蓝屏，属②）。

**事件三：帧预算被自己吃满 + vsync 级补传**
`dsh_engine.log:792114812`–`792129453` 一段里，`RTX VSR 16.59 → 18.46 → 18.56 ms/帧`，同期 `Vulkan 上传+渲染 16.89 → 21.19 → 22.89 → 20.94 ms`，两项相加已 35–41 ms，是 60 fps 预算（16.7 ms）的 2 倍以上。全日志最差点在 `2403: [792439796] 48.11 ms`（媒体时间才 5.098 s），2.5 s 后日志出现 `RTX VSR: 已关闭`——**这是"开 VSR 就卡、关掉才恢复"的直接现场**。另一条独立故障是补传：`791078`、`791645` 两簇共 23 条 `D3D11 回退：已补传最后一帧（vkOn=1 vkHasFrame=0）`（最长 14 连发），以 15–31 ms 间隔（≈每 vsync）连续重传全帧。同期前端记录 1 次 `C# 渲染回调停摆 4.5 秒`（`dm_debug.log:2595`），引擎记录 3 次冻结看门狗。**"VSR + 回读"这条路径的帧预算结论：8.55 + 11.44 ≈ 20 ms > 16.7 ms，不可能稳 60。**

**事件四：版本错配让"白屏可读化"整条链失效**
`dm_debug.log:36`：`显卡判死探测不可用（EntryPointNotFoundException）—— 引擎未加载或 DLL 版本较旧；界面将不做提示`，此后 23 次重复，每次启动/换片都重抛。同期 `DshEngine_SetRtxSdkPath` 也找不到（5 次）。安装目录 `WinUIGui.exe`(10-26) 与 `dsh_engine.dll`(10-23) 相差 3 天。结果：设备一旦丢失，前端**连横幅都不会弹**，用户只看到白屏——与 `01-engine-core.md` P0-1（源码里 `DshEngine_GpuDead` 被删）互为独立佐证。

**事件五（工作区旧日志）：独占模式固定 16 bit / 48 kHz**
`app\crash.log`（8-30）第 4 行：`WASAPI 输出: 独占模式 (exclusive) @48000Hz 2ch 16bits`，而同一段第 3 行媒体信息是 `音频 0Hz/0ch`、`硬解=d3d11va`，第 2 行又写 `[解码] 使用 Vulkan Video 硬解（无D3D11冲突）`——**同一份日志里解码路径自相矛盾**，且独占协商完全不看源格式。现场日志侧只有 1 次独占尝试且从未生效（K 行）。

## 5. 结论：最该优先修的真实问题（按证据强度）

1. **音轨提前 EOF → 主时钟停摆 → 假"结束"重播（①，37 次，同一文件同一毫秒位）**。修 `av_read_frame` 返回 `AVERROR_EOF` 时的时钟兜底（切墙钟、标记 audio-eof），并让"结束判定"必须 `nearEnd=True` 或 `audio+eof` 双条件成立。验收：`播放结束` 后 `pos/dur` 差 <1 s 且不出现 `stalled=True`。
2. **导出面版本错配导致设备丢失检测全线静默（①，24+5 次）**。给 `dsh_engine.dll` 加 `DshEngine_GetApiVersion()`，C# Init 后强校验；不匹配时 UI 明示并禁用 VSR/判死按钮，而不是每秒抛一次 `EntryPointNotFoundException`。
3. **渲染帧预算超支 + vsync 级补传风暴（①，p50 11.44 / max 48.11 ms，38 次补传、最长 14 连发）**。VSR 与上传必须择一或降档；`vkHasFrame=0` 时的补传要限一次而不是每帧重试。
4. **Init/Shutdown 不配对（①，4 组、13 次多余 Init、113 ms 内 3 次建交换链）**。Init 前必须幂等关闭旧设备；给"60 s 内重建 >3 次"加熔断（对应历史 41 次风暴）。
5. **日志自身是噪声源（①，98.1% / 71% 是心跳）**。`TICK`、`DM: TICK`、`[性能]` 降到 5 s 一条并落到环形缓冲；补日期、加轮转（单文件 ≤8 MB），否则下一次故障仍然只能靠猜。
6. **独占模式形同虚设（①，1 次尝试 0 次生效）**。要么真协商（按源格式试 24 bit / 44.1k），要么在 UI 上标"当前不可用"，不要留一个永远无效的开关。
7. **94 条 `SocketException 995` 未观察异常（①，签名全同）**。后端监督 socket 在进程退出时被中止且无人 await；虽是噪声，但在终结器线程重抛，属潜在崩溃面。
8. **`dm_recv.log` 33 条/秒的 `VIEWWH` 且无任何弹幕接收记录（①）**——这份日志对弹幕诊断零价值，纯占 39 KB 与 IO。

## 6. 取证局限

1. **两份主日志都没有日期**：`dsh_engine.log` 只有开机毫秒 tick（中间还有 1 次重启重置、5 段 >10 min 空洞、最长 84,858 s ≈ 23.6 h），`dm_debug.log` 只有 `HH:mm:ss.mmm` 且**跨天追加、无会话分隔**（5 次时间倒退最大 −4.6 h）。因此**跨文件的分钟级对齐只能靠内容巧合**（例如 237 s 的 EOF 与 `pos=235633` 的吻合），不能做严格时序证明。
2. **引擎完全没有设备丢失日志**：`DEVICE_REMOVED`、`0x887A0005`、`失败`（仅 3 条且都是 `av_read_frame`）全为 0，"41 次重建风暴/整机蓝屏"在本日志中**无法证实**；只能看到 Init 风暴这一同类前兆。
3. **打开媒体耗时不可测**：`LoadMedia 步骤` 与 `LoadMedia ok` 同一 tick，引擎不打起点/终点。
