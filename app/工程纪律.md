# 工程纪律与已知陷阱（local-media-player）

> ## ★★ 2026-10-17 最新状态（覆盖下文第一节）
> `WinUIGui.csproj` 那条自动拷贝**已从结构上修复**：改为 `Condition="'$(CopyEngine)' == 'true'"`（**显式选择才生效**）。
> 实测契约（当天逐项验证）：
>
> | 命令 | 对 bin 里引擎的影响 |
> |---|---|
> | `dotnet build -c Debug`（**增量**） | ★ **完好保留**（实测 `6E034401 → 6E034401`）✔ —— **日常改 C# 用这个** |
> | `dotnet build -c Debug -t:Rebuild` | ⚠️ **会删掉** bin 里的引擎（先 Clean 整个输出目录，csproj 又不再补回）→ **交付变成"引擎缺失"，视频打不开** |
> | `dotnet build -p:CopyEngine=true` | 会从 `dsh_engine\` 拷一份（**可能是旧的/队友的中间产物**）→ 仅用于全新环境 |
> | ★ **`deploy.ps1`** | 编译到独立 scratch → **先编 C# → 再拷引擎 → 部署后最终复核** —— **唯一正确的交付方式** |
>
> **结论：日常增量构建；要交付一律 `deploy.ps1`；永远不要拿 `-t:Rebuild` 直接对交付目录动手。**

> 这份文件是**给未来的我/队友看的**：哪些坑已经踩过、为什么、怎么避免。

## 一、★ 构建/部署类（最容易造成"跑的不是我以为的那份代码"）

### 1. `WinUIGui.csproj` 会自动把引擎拷进 bin
```xml
<None Include="..\dsh_engine\dsh_engine.dll" Condition="Exists(...)">
  <CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>
  <Link>dsh_engine.dll</Link>
```
**后果**：每次 `dotnet build`（尤其 `-t:Rebuild` 会先清空输出）都会把 `dsh_engine\` 里的引擎拷进 `bin`，
**把刚部署的那份覆盖掉**。2026-10-17 因此把"进行中的版本"带进过交付目录两次，并让"部署校验"形同虚设。
**规矩**：
- ★ **引擎的构建输出绝不写 `dsh_engine\dsh_engine.dll`**（那是共享路径）—— 写自己的 scratch（`_avc_probe\build\`、`_tmp_swr\build\`）；
- ★ `deploy.ps1` 的固定顺序：**先编 C# → 再编并拷引擎 → 最后做"部署后最终复核"**（不一致直接退出码 1）；
- ★ **`Copy-Item` 保留源时间戳** → 看时间判断部署是否成功一定出错，**必须比 MD5**。

### 2. 部署前必须检查占用
有人（用户或队友探针）正在用 DLL 时部署 → 链接失败或把别人的进程弄挂。
`deploy.ps1` 检测到 `WinUIGui` 运行会**拒绝部署**（绝不杀进程）。

### 3. ffmpeg 运行期依赖
`bin` 下必须有：`avfilter-10.dll` / `postproc-58.dll` / **`swresample-5.dll`** / `avcodec-61` / `avformat-61` / `avutil-59` / `swscale-8`。
缺任何一个 → 引擎整个加载失败 → **视频打不开**（历史事故）。

## 二、★ FFmpeg 头文件的 `extern "C"` 在本机不生效
用头文件声明编出来是 **C++ 修饰名**（`_Z20avfilter_get_by_namePKc`），而导入库里是 **C 符号**（`nm libswresample.dll.a` 显示 `T swr_convert`）→ **链接必然 undefined**。
**两台都栽过**：`avfilter_get_by_name`（历史）与 `swr_*`（2026-10-17）。
**解法（照抄即可）**：在 `audio_out.h` 里**自己 `extern "C"` 声明原型**并**不 include 对应头文件**（现成样板：`AVF_DECL_FIXED` / `SWR_DECL_FIXED`），链接加 `-lavfilter` / `-lswresample`。
★ **库文件一直是好的** —— 别再怀疑"导入库坏了"。

## 三、★ 测试纪律（都出过事故）
1. **出声测试同一时刻只允许一个人**，开始前先在回复里报备（`_test_volume_saved.txt` 被并发覆盖过两次）。
2. 出声前 `set_test_volume.ps1`（压 2%），测完 `-Restore`，★ **并手工确认 `data\player_settings.json` 的 `volume=1`**（该脚本的 `-Restore` 三次写回中间值；现已加"保存值<0.05 时拒绝恢复并告警"的防坑检查）。
3. 只加载**快照副本**测；**绝不**以交付目录为写目标。
4. 能用 `DSH_NO_AUDIO=1` 静音跑就静音跑。

## 四、★ "哪个文件是活的"必须用运行证据确认
2026-10-17 真实教训：改了半天的 `backend/app/api.py`（FastAPI 实现）**是遗留代码** —— venv 里没有 fastapi、**全仓库无人 import 它**；真正生效的是 `stdlib_server.py → services.py`。
**规矩**：判断代码是否生效，**起服务打接口 / 看日志新行 / 看 dump 指纹**，**不要靠文件名或目录结构猜**。
（同类：探针若是静态包含头文件编的，改完源码不重编探针就会得出"旧二进制"的结论。）

## 五、★ 自动恢复必须有上限 + 停机阀门
历史事故：设备丢失后无上限重建，**每帧重建 247 次 → 整机蓝屏**（`nvlddmkm.sys+28242f`）。
现行阀门：**60 秒窗口内最多 3 次重建（成功也计数）** + 抖动检测（重建成功后 ≤10s 又丢 → 记失败）+ 判死后**停止向显卡提交任何东西**。
★ 另一个容易漏的点：只统计"连续失败"的阀门**拦不住"重建成功→立刻又被移除"**这种模式（实测循环 41 次未判死）。

## 六、★ 写作用域与协调
- 任务卡上的 `write_scopes` 是**承诺**：即使是 Lead，动别人的范围**也必须先协调**（发消息或改范围）。
- 实例：Lead 为支持 3× 倍速直接改了 `audio_out.h` 的一行 clamp，而该文件当时归队友 —— 队友在自己交付后 37 秒发现文件被重写并上报，做得对。
- ★ **只跟"自己的旧副本"diff，分不出"我改的"和"别人改在我区域里的"** —— 必须**逐行读复核区域本身** + 比封存副本的 hash。

## 七、其他小坑
- PowerShell 的 `String.Replace` **只接受两个参数**（三参数会抛异常，却可能照样打印"✔"）→ 改完必须 `Select-String` 复查。
- 改代码**整块替换**并立刻编译；**不要做行手术**（`audio_out.h` 因此被破坏过两次）。
- C# 里每个 `[DllImport]` **必须紧跟自己的 `extern`**（错位会让 `SetVolume` 丢特性 → 运行时 `ERROR_BAD_FORMAT(0x8007000B)`，用户看到"音量永远是最大"）。
