# A. 当前线（WinUI 3 + `dsh_engine.dll`）· 未做清单
> 最后更新 2026-10-14。依据：`CHANGELOG.md` 中的实测记录（每条都有命令/数字）。

## A.0 当前线的形状（先明确，免得拿老线清单瞎对标）
| 环节 | 现状 |
|---|---|
| 渲染 | **D3D11**（默认）／**Vulkan**（`DSH_GRAPHICS=vulkan`，可选；见 `vulkan_video.h`） |
| 解码 | FFmpeg **软解** → swscale → BGRA8 / 10bit 打包 |

| 界面/后端 | C# WinUI 3 ＋ Python（stdlib HTTP 127.0.0.1:8765）＋ SQLite |

## A.4 诊断开关（当前线，长期留用）
| 变量 | 作用 |
|---|---|
| `DSH_GRAPHICS=vulkan` | 视频改由 Vulkan 渲染（另有 `PLAY_VULKAN.bat`） |
| `DSH_VULKAN_NEVER=1` | 从不启用 Vulkan（隔离"环境变量本身"与"Vulkan 渲染过"） |

| `DSH_DANMAKU_CPU=1` | 弹幕强制走旧 CPU 路径（A/B 对比） |
| `DSH_HDR_PASSTHROUGH=1` | 启动即 HDR 直通 |
| `DSH_WASAPI_EXCLUSIVE=1` | 音频走 WASAPI **独占**（按源采样率，位完美；会占住设备 ✗） |
| `DSH_NO_DM=1` | 只画视频不画弹幕（确认画面里"带"是不是弹幕） |
| `DSH_ENGINE_LOG=0` | 关引擎日志 |


## A.5 白屏 / 设备丢失（2026-10-16 结案）
| 项 | 状态 |
|---|---|
| 显卡设备被移除（`0x887A0005`）后的**重建风暴** | ★ **已根治**：阀门改为"60 秒窗口内最多 3 次重建（成功也计数）"+ 抖动检测（成功 ≤10s 又丢记失败）→ 事故时 41 次循环变成 3 次内停机 |
| 风暴的**根因** | ★ **已修**：`dsh_rebuild_device()` 漏了作废 Vulkan 互操作状态（共享纹理/导入句柄/内存未释放）→ 新设备继续用被移除设备上的资源 → 立刻再丢。现在重建开头先 `vk.shutdown()`+`CloseHandle`+`Release` 再释放 D3D11 |
| ★ **"第一次"丢失的原因** | ✅ **2026-10-17 查明**：不是驱动、不是跨 API 互操作 —— 是**界面「连播结束判定」跨片状态不清零**（`VideoWindow.xaml.cs:1409-1444` 的 `_lastEndPos/_lastEndStall` 在换片时没清零，`:1853` 只复位了 `_eofHandled`）→ 新集刚打开 0.5 秒就被误判"已结束" → 每 0.5 秒重开同一个文件 → **引擎被拆建 42 次 / 交换链 88 条**（事故日志实测） → 驱动被压垮 → `DEVICE_REMOVED` → 白屏。修复：T22（清零全部状态 + 2 秒武装延迟 + "真的在播"门槛 + 同路径闸门 + 硬上限）。★ 完整证据链见 `CHANGELOG.md` 2026-10-17G |（本地复现失败：12 次 Vulkan 换片 + 15 次 d3d11 换片，0 次丢失）。新增逐步日志 `LoadMedia 步骤[t=…]` / `纹理重建[t=…]` / `Vulkan: 渲染目标`，下次真机复现可定位 |
| 界面表现 | 判死时显示文字提示条「显卡设备已丢失（驱动故障）…请重新打开播放器」并把控件置灰（自带实测：UIA 逐秒时间线 + 反向无误报） |
| 适配器可见性 | 启动即打印所有 DXGI 适配器 + `IDXGIDevice::GetAdapter` 查"实际在用哪块" + Vulkan 物理设备名 + 是否同卡告警；`DSH_GPU=nvidia\|intel\|amd\|auto` 可强制 |
| 已证伪的假设 | ①keyed mutex 缺失（`vkWaitForFences` 已串行化）②换分辨率会重建共享纹理（共享纹理是窗口尺寸）③"必须重启机器"（只重开播放器即恢复） |
| 相关诊断开关 | `DSH_TEST_DEVICE_LOST=ok\|1\|dead\|flap`（注入设备丢失/抖动，用于回归阀门） |

基于神经网络的实时超分 (AI Super-Resolution)	在端侧利用AI模型将低分辨率画面实时放大，提升清晰度并去除压缩噪声	百度等云厂商已提供端上超分SDK，在本地通过模型推理提升画质，对设备性能要求较高。芒果TV也自研了端智能超分方案。
亮度-色度联合去色带 (Joint Luminance-Chrominance Debanding)	专门针对编码压缩产生的色带问题，同时处理亮度和色度通道	针对HDR/WCG内容，有研究工作专门解耦亮度和色度通道进行去色带。
位深扩展 (Bit-Depth Expansion, BDE)	将低色深视频（如8bit）扩展至高色深（如10bit），恢复平滑渐变，并校正色彩	此技术旨在从算法层面“补”回压缩时丢失的色彩信息。
🎥 帧率与运动处理
算法/技术方向	核心作用	说明
基于运动估计的帧率提升 (FRUC)	通过分析前后帧的运动矢量，智能生成中间帧，提升视频流畅度	专业级算法，包含双向运动估计、运动矢量平滑、运动补偿等复杂步骤。
时域超分 (Space-Time VSR)	同时提升视频的空间分辨率（超分）和时间分辨率（帧率）	这是视频超分领域的前沿方向，需要同时建模精细纹理和平滑运动。
🛠️ 其他专业级工具
算法/技术方向	核心作用	说明
基于RAW数据的超分 (RAW Video VSR)	直接处理相机原始RAW数据，避开传统ISP处理流程，获得更高画质上限	学术界的研究方向，能最大化利用传感器信息，对低光和噪声环境效果更好。
专业框架中的降噪与去色带 (VapourSynth)	使用专业视频处理框架进行深度降噪和去色带	像VapourSynth这类专业工具，在去色带时支持精细调整检测范围和抖动强度。

🚀 前沿画质提升技术
技术方向	核心作用	应用案例与说明
AI 实时超分辨率 (Super-Resolution)	利用AI模型，在端侧实时将低分辨率视频放大（如360P→720P），提升清晰度并去除压缩带来的块效应。	百度、芒果TV、腾讯视频、爱奇艺等都已推出端侧AI超分方案。一些第三方播放器也集成了如Real-ESRGAN等开源超分算法。
AI 智能插帧 (Frame Interpolation)	分析前后帧的运动，智能生成中间帧，提升视频流畅度，用于慢动作或改善低帧率视频的卡顿。	苹果在 WWDC25 上展示了基于机器学习的帧率转换功能。也有专利方案利用扩散Transformer架构的插帧模型来提升流畅度。
AI 时域降噪 (Temporal Denoising)	通过分析前后多帧画面来消除噪点和压缩伪影，让画面更纯净，同时优化压缩效率。	苹果的 Video Toolbox 框架已提供基于机器学习的时域降噪特效。
设备与内容自适应增强	根据显示设备的能力（如是否支持HDR）和网络带宽，动态决定画质增强的强度，避免无效计算或卡顿。	相关专利描述了根据“播放环境参数”（如显示参数、传输环境）来动态调整质量提升策略的方案。
